# 20260808 Agent 实现思路

## 1. 项目定位

当前 nano-vLLM 改进项目已经完成了 PD 分离原型、persistent prefill/decode worker、Shared Memory / sync_gpu KV Handoff、异步 send/recv、backpressure、benchmark matrix 与 correctness 对拍。下一步如果要快速接入 Agent 相关能力，重点不应放在做一个简单的工具调用 Demo，而应放在：

**让 Agent 编排层的“认知调度”和推理引擎层的“物理调度”形成双向反馈。**

也就是说，Agent 层负责理解任务复杂度，推理引擎层负责暴露真实执行负载，二者之间通过一个轻量级调度器连接起来，从而解决 Agent workload 中常见的长短任务混排、工具调用次数不均、prefill/decode 压力不均衡等问题。

核心链路可以抽象为：

```text
Agent Request
  -> 任务复杂度预估
  -> 负载感知调度器
  -> P/D Worker 或 Engine 实例路由
  -> 推理执行与指标回传
  -> 调度器更新负载状态
```

这个方向的价值在于：项目亮点不再是“会调用 Agent 框架”，而是“能够根据 Agent 任务特征优化底层推理资源调度”。

## 2. 为什么适合当前项目

Agent 系统中的请求复杂度差异很大：

- 简单问答通常是短 prefill、短 decode。
- 长文档总结是长 prefill、较长 decode。
- 工具调用任务可能包含多轮 LLM 调用，任务链路更长。
- 多步骤规划任务可能生成更长输出，并持续占用 decode worker。

如果使用传统 round-robin 或随机分配，请求很容易被分配到已经拥塞的 worker，导致部分 GPU 长时间排队，而另一部分 GPU 负载不足。

当前项目的优势是 nano-vLLM 推理引擎可控，并且已经具备 PD 分离结构，因此可以直接暴露和利用以下底层指标：

- prefill worker 的等待队列长度。
- decode worker 的 active decode request 数量。
- 当前 active sequences 数量。
- pending sends / pending recvs 数量。
- KV transfer / restore latency。
- decode token/s。
- 每个请求的 input tokens / output tokens。

这些指标正好可以作为 Agent 调度器的物理负载反馈。

## 3. 总体架构

推荐先做一个最小可用版本，不急着直接接 OpenAI Agents SDK 或 Claude Agent SDK。第一阶段可以用轻量 Agent request simulator 代替真实 Agent 框架，先把调度链路跑通。

```text
真实/模拟 Agent 请求集
  -> Request Profiler
  -> Complexity Estimator
  -> Load-aware Scheduler
  -> nano-vLLM PD Runtime
  -> Metrics Collector
  -> Scheduler Feedback
```

各模块职责：

### 3.1 Request Profiler

负责从真实数据集中提取请求特征：

- prompt。
- input_tokens。
- target_output_tokens。
- task_type。
- profile。

对于真实 Agent 请求，还可以额外记录：

- 是否需要工具调用。
- 预估工具调用次数。
- 预估子任务数量。
- 是否属于长上下文任务。

### 3.2 Complexity Estimator

第一版不需要模型预测，可以使用规则估计：

```text
complexity_score =
  input_tokens * prefill_weight
+ target_output_tokens * decode_weight
+ estimated_tool_calls * tool_weight
+ estimated_steps * step_weight
```

建议先简化成：

```text
complexity_score = input_tokens * 0.3 + target_output_tokens * 1.0
```

原因是 decode 阶段通常是逐 token 生成，长期占用 decode worker，对 serving latency 和吞吐影响更明显。

### 3.3 Load-aware Scheduler

调度器维护每个 worker 的动态负载状态：

```text
worker_state = {
  "worker_id": "...",
  "role": "prefill/decode/pd_pair",
  "queue_len": ...,
  "active_decode_requests": ...,
  "pending_sends": ...,
  "pending_recvs": ...,
  "recent_decode_tok_s": ...,
  "recent_restore_time_s": ...
}
```

最小化负载评分函数：

```text
load_score =
  queue_len * queue_weight
+ active_decode_requests * decode_weight
+ pending_sends * send_weight
+ pending_recvs * recv_weight
+ estimated_tokens / capacity
```

调度策略：

- baseline：round-robin。
- candidate：load-aware，即选择 load_score 最低的 worker。

第一版只需要比较这两种策略即可。

### 3.4 nano-vLLM PD Runtime

当前已有 PD runtime 可以继续复用：

- persistent prefill worker。
- persistent decode worker。
- shared_memory KV transfer。
- sync_gpu KV transfer。
- async pending send/recv。
- backpressure。

Agent 调度器不需要直接改 KV 传输逻辑，只需要决定请求提交到哪个 worker 或 worker pair。

### 3.5 Metrics Collector

需要统计：

- TTFT。
- E2E latency。
- throughput generated tok/s。
- decode token/s。
- prefill time。
- transfer time。
- restore time。
- queue wait time。
- p50 / p90 / p99 latency。
- worker load imbalance。

其中 worker load imbalance 可以先用简单指标：

```text
imbalance = max(worker_busy_time) / avg(worker_busy_time)
```

如果 load-aware 策略能够降低 imbalance，同时提升吞吐或降低 tail latency，就可以形成比较清晰的项目亮点。

## 4. 与真实数据集 Benchmark 的结合

在接 Agent 之前，应该先把真实 serving workload 建起来。推荐数据集顺序如下：

### 4.1 ShareGPT

优先级最高。适合模拟真实聊天请求长度分布，也贴近 vLLM serving benchmark 的常见设置。

用途：

- chat_real_mix。
- short_in_short_out。
- short_in_long_out。
- mixed_chat。

### 4.2 LMSYS-Chat-1M

更大规模的真实对话数据，适合做更真实的多轮聊天负载。

用途：

- 大规模 chat workload。
- 中文/英文混合负载。
- 长短请求混合调度。

### 4.3 LongBench

适合长上下文压力测试，不一定直接代表线上聊天流量，但非常适合验证 PD 分离对 prefill-heavy workload 的意义。

用途：

- long_in_short_out。
- long_in_long_out。
- KV transfer / restore latency 分析。

### 4.4 BurstGPT

适合做真实到达模式和 burst 流量压测。

用途：

- open-loop request rate。
- trace replay。
- tail latency。
- SLO violation。

## 5. 数据格式

建议所有真实数据集先统一转换成当前 benchmark 已经支持的 jsonl schema：

```json
{
  "request_id": "sharegpt_000001",
  "prompt": "...",
  "input_tokens": 512,
  "max_tokens": 128,
  "output_len": 128,
  "total_tokens": 640,
  "profile": "chat_real_mix"
}
```

Agent 调度版本可以在此基础上扩展字段：

```json
{
  "request_id": "agent_000001",
  "prompt": "...",
  "input_tokens": 512,
  "max_tokens": 128,
  "output_len": 128,
  "total_tokens": 640,
  "profile": "agent_tool_mix",
  "task_type": "tool_qa",
  "estimated_steps": 3,
  "estimated_tool_calls": 2,
  "complexity_score": 281.6
}
```

## 6. 负载测试方式

### 6.1 Batch / Pipeline 模式

这是当前已有模式：measure 阶段一次性投递请求。

优点：

- 最容易复用当前 benchmark。
- 适合检查 PD pipeline 是否跑通。
- 适合比较 shared_memory 与 sync_gpu。

缺点：

- 不是真正的线上 serving 到达模式。
- 无法准确体现 QPS、排队与 SLO。

### 6.2 Closed-loop 并发模式

维护固定 in-flight 请求数：

```text
concurrency = 1 / 2 / 4 / 8 / 16
```

每完成一个请求，就提交下一个请求。

优点：

- 改动较小。
- 很适合当前 persistent worker 架构。
- 能观察系统吞吐随并发上升的变化。

建议优先实现。

### 6.3 Open-loop QPS 模式

按照固定 request rate 提交请求：

```text
request_rate = 0.5 / 1 / 2 / 4 / 8 req/s
```

或者使用 BurstGPT 的真实 timestamp 进行 trace replay。

优点：

- 更接近线上 serving。
- 能测试排队、拥塞、tail latency。
- 适合和 Agent 调度策略结合。

缺点：

- benchmark driver 需要更多调度逻辑。
- 对 worker 错误处理和 timeout 要求更高。

## 7. 两周推进计划

### 第一步：真实数据集转换

目标：

- 实现 ShareGPT 转换器。
- 输出 `data/serving_benchmarks/sharegpt_qwen3_tokenized.jsonl`。
- 保持字段兼容当前 benchmark。

验证：

- 使用现有 pipeline benchmark 跑 `LIMIT=20` smoke。
- 对比 shared_memory 与 sync_gpu correctness。

### 第二步：closed-loop benchmark

目标：

- 在当前 pipeline benchmark 基础上新增 closed-loop 提交模式。
- 支持 `--concurrency`。
- 输出按 concurrency 分类的 summary。

验证矩阵：

```text
backend = shared_memory / sync_gpu
profile = chat_real_mix / long_in_short_out / mixed_chat
concurrency = 1 / 2 / 4 / 8
```

### 第三步：调度策略对比

目标：

- 实现 round-robin baseline。
- 实现 load-aware scheduler。
- 对比两种策略下的吞吐、平均延迟、p90/p99 latency、worker imbalance。

第一版 worker 可以不是真正多个复杂部署，先用多个 worker pair 或模拟多 worker 状态也可以。重点是调度链路和指标闭环成立。

### 第四步：Agent SDK 接入

目标：

- 接入 OpenAI Agents SDK 或 Claude Agent SDK。
- Agent 层只负责生成任务和工具调用。
- 推理请求统一走自研调度器。

这一阶段的重点不是 Agent 框架本身，而是证明：

```text
Agent 复杂度信息可以影响底层推理资源调度。
底层推理负载指标可以反馈给 Agent 调度层。
```

## 8. 简历表达方向

可以包装为：

```latex
\datasection{\item \textbf{Agent-aware Serving 调度：} 面向 Agent workload 中任务复杂度差异大、工具调用链路长短不一导致的 GPU 负载不均问题，基于自研 nano-vLLM PD 分离推理引擎，设计任务复杂度感知的负载调度器，将 Agent 编排层的 token / step / tool-call 复杂度预估与推理引擎层的 queue length、active sequences、pending transfer 等实时负载指标关联，实现请求在 Prefill / Decode 资源池间的动态路由。}
```

如果 benchmark 跑出结果，可以继续补：

```latex
\datasection{\item \textbf{真实负载评测：} 基于 ShareGPT / LMSYS / LongBench 构建真实请求长度分布与长上下文评测集，对比 round-robin 与 load-aware 调度策略，统计 TTFT、E2E latency、p90/p99 tail latency、decode token/s 与 worker load imbalance，验证 Agent-aware 调度在混合负载下的吞吐与延迟收益。}
```

注意：简历中不要直接写外部论文宣称的 1.5-3.6 倍作为自己的结果。可以作为目标或参考，但最终应写自己 benchmark 得到的数据。

## 9. 当前最推荐的下一步

最推荐按以下顺序推进：

```text
ShareGPT 转换器
  -> 真实数据集 pipeline smoke
  -> closed-loop concurrency benchmark
  -> round-robin vs load-aware scheduler
  -> Agent SDK demo 接入
```

这样做的好处是每一步都能独立产出结果，不会因为 Agent 框架接入卡住而影响主项目推进。同时，这条路线和当前 PD 分离、sync_gpu KV transfer、异步 pending send/recv、benchmark matrix 都是连续的，不会显得像硬塞一个无关 Demo。
