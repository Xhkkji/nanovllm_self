# 元数据结构信息

本文整理 `nanovllm_self` 中与在线化、PD 分离、KV handoff、流式输出相关的核心元数据结构。

核心原则：

```text
Sequence 是模型执行态
RequestState 是服务请求态
HandoffPayload 是 prefill -> decode 的交接单
KVTransferMeta 是 KV 数据位置说明
DecodeStepOutput 是 decode 单步执行结果
TokenEvent 是对外流式输出事件
```

## 1. HandoffPayload 是什么

定义位置：`pd_self/payload.py`

`HandoffPayload` 是 **prefill worker 交给 decode worker 的轻量交接对象**。

它不是请求本身，也不是 KV cache 本体，而是：

```text
decode 端恢复这条请求所需的最小信息
+
这条请求对应的 KV 数据在哪里
```

可以理解为：

```text
HandoffPayload = 快递单
KV cache blocks = 真正的大件货物
KVConnector / KVStore = 仓库和运输系统
DecodeEngine = 收货方
```

完整链路：

```text
PrefillEngine.step()
-> HandoffPayload
-> DecodeEngine.restore_payloads()
-> DecodeEngine.restore_sequence()
```

## 2. HandoffPayload 字段解释

当前结构：

```python
@dataclass
class HandoffPayload:
    seq_idx: int
    request_id: str
    token_ids: List[int]
    num_prompt_tokens: int
    num_cached_tokens: int
    temperature: float
    max_tokens: int
    ignore_eos: bool
    finished: bool
    transfer_meta: Optional[KVTransferMeta] = None
```

### 2.1 seq_idx

内部执行序号。

用于：

- scheduler 内部定位 seq
- `seq_to_request` 映射
- 测试中保持输出顺序

它不是用户请求 ID。

### 2.2 request_id

服务层请求 ID。

用于：

- 在线系统识别用户请求
- streaming event 归属
- abort / cancel / timeout
- request state 查表

注意：在线化后 `request_id` 应该从 `Sequence.request_id` 继承，不能在 handoff 时临时拼。

当前需要注意的代码点：

```python
request_id=f"req-{seq.seq_idx}"
```

应该改成：

```python
request_id = getattr(seq, "request_id", None) or f"req-{seq.seq_idx}"
```

否则 `OnlinePDCoordinator.submit()` 里生成的真实 `request_id` 会丢失。

### 2.3 token_ids

当前完整 token 序列。

在当前 PD handoff 边界下，它通常是：

```text
prompt tokens + 第一枚生成 token
```

原因是当前 handoff ready 条件是：

```python
return seq.is_prefill_done and seq.num_completion_tokens >= 1
```

也就是 prefill 端不仅做完 prompt，还已经采样出了第一枚 token。

### 2.4 num_prompt_tokens

原始 prompt 长度。

用于区分：

```text
prompt 部分
completion 部分
```

例如：

```python
completion_ids = payload.token_ids[payload.num_prompt_tokens:]
```

在线 coordinator 中类似逻辑是：

```python
state.output_ids = payload.token_ids[len(state.input_ids):]
```

本质都是用 prompt 边界切出 completion。

### 2.5 num_cached_tokens

真正已经写入 KV cache 的 token 数。

这个字段非常关键。它不一定等于 `len(token_ids)`。

在当前 handoff 边界下，常见情况是：

```text
token_ids = prompt + first generated token
num_cached_tokens = prompt length
```

因为第一枚生成 token 已经 append 到 `token_ids`，但它的 KV 通常还没写入 cache。

所以 KV 导出必须基于：

```python
seq.num_cached_tokens
```

不能基于：

```python
len(seq.token_ids)
```

### 2.6 temperature / max_tokens / ignore_eos

采样参数。

decode 端恢复 `Sequence` 后，需要继续沿用 prefill 端请求的采样配置。

### 2.7 finished

表示这条请求是否在 prefill 端就已经完成。

例如：

```text
max_tokens = 1
prefill 端已经生成了第一枚 token
```

这时请求已经完成，不需要进入 decode 端。

此时：

```text
payload.finished = True
payload.transfer_meta = None
```

### 2.8 transfer_meta

指向 KV 数据的元信息。

它不是 KV tensor 本体。

如果 `finished=True`，可以没有 `transfer_meta`。

## 3. HandoffPayload 不应该放什么

`HandoffPayload` 不应该直接放大 tensor。

不要这样设计：

```python
payload.kv_blocks = huge_tensor
```

原因：

- payload 应该轻量
- 真正 KV 数据可能在 GPU、CPU、shared memory、远端 KV store
- 后续要对齐 vLLM / Mooncake，payload 应该只携带 metadata

当前方向是：

```text
HandoffPayload.transfer_meta
-> KVTransferMeta
-> SharedMemoryKVRef / handoff_id
-> KVStoreBackend
```

## 4. Sequence：模型执行对象

定义位置：`nanovllm/engine/Sequence.py`

`Sequence` 代表 scheduler / model_runner 里真正执行的一条序列。

包含：

- `seq_idx`
- `request_id`
- `token_ids`
- `block_table`
- `num_prompt_tokens`
- `num_cached_tokens`
- `num_new_tokens`
- `temperature`
- `max_tokens`
- `ignore_eos`
- `status`
- `blocked_reason`

职责：

```text
scheduler 调度它
model_runner 根据它准备 input
block_manager 根据它管理 KV block
postprocess 给它 append token
```

一句话：

```text
Sequence = 模型执行态
```

它不是完整的服务请求对象。

## 5. RequestState：服务层请求对象

定义位置：`pd_self/request_state.py`

`RequestState` 代表在线服务中的一个用户请求。

包含：

- `request_id`
- `seq_idx`
- `prompt`
- `input_ids`
- `output_ids`
- `status`
- `handoff_payload`
- `stream_queue`
- `created_time`
- `finished_time`
- `error`

职责：

```text
OnlinePDCoordinator 用它追踪请求生命周期
streaming 用它保存 token event
abort / finish / error 都落在它上面
```

一句话：

```text
RequestState = 服务层请求态
```

它和 `Sequence` 的区别：

```text
RequestState 是“用户请求”
Sequence 是“模型执行实例”
```

两者通过：

```python
seq_idx
request_id
```

关联。

## 6. TokenEvent：流式输出事件

定义位置：`pd_self/request_state.py`

当前结构：

```python
@dataclass
class TokenEvent:
    request_id: str
    token_id: int | None
    text: str = ""
    finished: bool = False
    finish_reason: str | None = None
    error: str | None = None
```

它代表：

```text
某个 request 新产出了一个 token
或者这个 request 结束了
或者这个 request 出错了
```

用途：

- streaming
- agent 接入
- OpenAI-compatible API

一句话：

```text
TokenEvent = 对外输出事件
```

## 7. DecodeStepOutput：decode 单步内部返回

定义位置：`pd_self/runtime_types.py`

当前结构：

```python
@dataclass
class DecodeStepOutput:
    scheduled: list
    token_ids: list[int]
    seq_need_compute_logits: list[int]
    finished_seq_ids: list[int]
```

它是 `DecodeEngine.step()` 返回给 `OnlinePDCoordinator` 的内部结构。

### 7.1 scheduled

本轮 decode 实际跑了哪些 `Sequence`。

### 7.2 token_ids

本轮采样出来的 token。

### 7.3 seq_need_compute_logits

`token_ids` 对应 `scheduled` 里的哪些局部下标。

例如：

```python
scheduled = [seq0, seq1, seq2]
seq_need_compute_logits = [0, 2]
token_ids = [100, 200]
```

表示：

```text
seq0 生成 token 100
seq2 生成 token 200
seq1 本轮没有需要采样的 logits
```

### 7.4 finished_seq_ids

本轮生成后完成的 seq。

一句话：

```text
DecodeStepOutput = decode worker 一步的内部执行结果
```

它不是对外事件。

对外事件应由：

```python
OnlinePDCoordinator._collect_decode_events()
```

转换成 `TokenEvent`。

## 8. KVTransferMeta：KV 传输元数据

定义位置：`pd_self/payload.py`

当前结构：

```python
@dataclass
class KVTransferMeta:
    handoff_id: str
    producer_id: str
    num_cached_tokens: int
    num_kv_blocks: int
    last_block_num_tokens: int
    src_block_table: List[int]
    storage_ref: Optional[SharedMemoryKVRef]
```

它描述：

```text
这份 KV 在哪里
有多少 block
最后一个 block 有多少有效 token
生产者是谁
```

它不存 KV tensor。

一句话：

```text
KVTransferMeta = KV 数据的位置和形状说明书
```

## 9. SharedMemoryKVRef：共享内存引用

定义位置：`pd_self/payload.py`

当前结构：

```python
@dataclass
class SharedMemoryKVRef:
    shm_name: str
    shape: tuple[int, ...]
    dtype: str
    nbytes: int
```

它是 shared memory backend 的定位信息。

decode 端可以靠它 attach 到共享内存：

```python
shared_memory.SharedMemory(name=ref.shm_name)
```

一句话：

```text
SharedMemoryKVRef = 跨进程打开共享内存的地址信息
```

## 10. KVStoreItem：KV backend 内部数据对象

定义位置：`pd_self/kv_store.py`

当前结构：

```python
@dataclass
class KVStoreItem:
    kv_blocks: torch.Tensor
    num_kv_blocks: int
    last_block_num_tokens: int
    storage_ref: SharedMemoryKVRef | None = None
```

它是 `KVStoreBackend` 内部用的数据对象。

对于 dict backend：

```text
kv_blocks 直接存 tensor
storage_ref = None
```

对于 shared_memory backend：

```text
kv_blocks = None
storage_ref = SharedMemoryKVRef(...)
```

一句话：

```text
KVStoreItem = KV backend 存取层的数据包装
```

## 11. ScheduleOutput：调度统计对象

定义位置：`nanovllm/engine/scheduler.py`

当前结构：

```python
@dataclass
class ScheduleOutput:
    seqs: list[Sequence]
    decode_seqs: list[Sequence]
    prefill_seqs: list[Sequence]
    new_prefill_seqs: list[Sequence]
    num_decode_tokens: int
    num_prefill_tokens: int
    token_budget_used: int
    token_budget_remaining: int
    blocked_decode: int = 0
    blocked_prefill: int = 0
    reason: str = "ok"
```

它的目标是描述：

```text
这一轮 scheduler 调了什么
用了多少 token budget
有没有因为 block 不够被卡住
为什么 schedule 为空
```

注意：当前 `schedule()` 还没有实际返回或写入这个结构。它目前只是定义了，还没有完全接入。

一句话：

```text
ScheduleOutput = 调度可观测性元数据
```

## 12. 完整链路图

```text
用户请求
  |
  v

  |
  v
Sequence
  |
  v

  |
  v

  |

          |
          +--> handoff_id / SharedMemoryKVRef
          |
          +--> KVStoreBackend / KVConnector
  |
  v

  |

  |
  v

  v

  |
  v

  |
  v

  |

```

## 13. 容易混淆的结构对比

### 13.1 HandoffPayload vs RequestState

```text
RequestState = 在线服务全生命周期
HandoffPayload = prefill -> decode 的一次性交接信息
```

`RequestState` 活得更久。  
`HandoffPayload` 只在 P/D handoff 时存在。

### 13.2 HandoffPayload vs KVTransferMeta

```text
HandoffPayload = 请求交接单
KVTransferMeta = KV 数据交接说明书
```

`HandoffPayload` 包含 `KVTransferMeta`。

### 13.3 KVTransferMeta vs SharedMemoryKVRef

```text
KVTransferMeta = 通用 KV transfer 元信息
SharedMemoryKVRef = shared memory backend 的具体地址
```

如果以后做 RDMA / CUDA IPC，`KVTransferMeta` 可以尽量保持稳定，只换 backend 或 ref 表达。

### 13.4 Sequence vs DecodeStepOutput

```text
Sequence = 被执行的请求状态
DecodeStepOutput = 某一次 decode step 的输出结果
```

`DecodeStepOutput` 是瞬时的，`Sequence` 是持续变化的。

### 13.5 DecodeStepOutput vs TokenEvent

```text
DecodeStepOutput = 内部执行结果
TokenEvent = 对外流式事件
```

不要让 `DecodeEngine` 直接生成 `TokenEvent`。

原因：

```text
DecodeEngine 不应该关心 request state / stream queue / API 格式
```

应由 `OnlinePDCoordinator` 把 `DecodeStepOutput` 转成 `TokenEvent`。

## 14. 当前最需要注意的问题

当前 `pd_self/prefill_engine.py` 的 `_make_payload()` 里如果仍然是：

```python
request_id=f"req-{seq.seq_idx}"
```

而 `pd_self/online_coordinator.py` 的 `submit()` 里是：

```python
request_id = request_id or f"req-{uuid.uuid4().hex[:12]}"
```

这两个 request_id 不一定一致。

可能出现：

```text
OnlinePDCoordinator.requests 里有 req-abcd1234
HandoffPayload 里却写 req-0
```

然后这里会出问题：

```python
state = self.requests[request_id]
```

优先修复方式：

```python
request_id = getattr(seq, "request_id", None) or f"req-{seq.seq_idx}"
```

这样能保证 `HandoffPayload` 继承真正的在线 request_id。
