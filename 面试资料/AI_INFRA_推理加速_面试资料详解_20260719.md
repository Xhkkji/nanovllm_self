1. **模型结构**

4. **调度 / batching / serving**

面试官通常不会只问一个点，而是会连续追问：

- 你知道这个概念

所以准备时不要背孤立名词，要按系统链路来理解。

## 3. vLLM 需要掌握什么

vLLM 是 AI infra 面试里最常被问的基准框架。你至少要把下面这些点讲顺。

### 3.1 核心定位

vLLM 的核心不是“一个模型推理脚本”，而是：

- 一个面向 serving 的 runtime
- 一个围绕 KV cache 管理构建的调度系统
- 一个追求吞吐、低延迟和高显存利用率的工程实现

### 3.2 必会概念

#### PagedAttention

你要能讲：

- 为什么传统连续 KV cache 不够好
- 页式 / block 式管理解决什么问题
- block table 如何映射请求到实际 cache
- 为什么这能减少碎片和提升多请求利用率

关键点：

- PagedAttention 是 vLLM 的核心符号
- 面试里经常被当作“你懂不懂推理框架”的分界线

#### Continuous batching

你要能讲：

- 新请求怎么插队
- 为什么不能等所有请求完结再组下一批
- 为什么这对吞吐和 GPU 利用率重要

#### Chunked prefill

你要能讲：

- 长 prompt 一次性 prefill 会阻塞 decode
- chunked prefill 把长 prompt 切块，和 decode 混合执行
- 主要目标是平衡 TTFT 和 ITL

#### Prefix caching

你要能讲：

- 共享前缀可以复用 KV cache
- 典型场景是多轮对话、系统 prompt、agent prompt
- prefix cache 的收益通常体现在 TTFT

#### CUDA Graph

你要能讲：

- 为什么 decode 适合 graph
- 为什么 prefill 更难 capture
- 为什么 graph 通常配固定 bucket

#### Disaggregated prefill

你要能讲：

- prefill 和 decode 拆成不同实例 / 集群
- 目的不是“多拆一点”，而是把 TTFT 和 ITL 分开优化
- 关键是 KV handoff 边界

### 3.3 vLLM 面试常追问

1. PagedAttention 为什么比传统 attention serving 更适合多请求场景？
   回答要点：它把 KV cache 做成 block/page 管理，避免连续大块内存带来的碎片；block table 让不同请求可以按块复用和回收 cache；多请求并发时更容易组织调度。
2. chunked prefill 为什么能改善尾延迟？
   回答要点：长 prompt 被拆成多个 chunk 后，不会一次性占住 GPU；decode 可以插进来，短请求也能得到资源；所以 TTFT 和尾延迟更稳定。
3. prefix caching 的 block 粒度和 hash 逻辑怎么设计？
   回答要点：通常按 token 序列和 block 边界计算稳定 hash；命中后复用对应 KV block；关键是 tokenizer、模型版本和前缀内容必须一致，否则不能复用。
4. CUDA Graph 为什么不适合动态 shape 的 prefill？
   回答要点：prefill 的长度和 batch 变化很大，capture 时 shape 不稳定；CUDA Graph 更适合固定输入尺寸的 steady-state 路径；动态 shape 会让 replay 的可行性变差。
5. disaggregated prefill 为什么比单体 unified engine 更容易控制 SLO？
   回答要点：prefill 和 decode 资源诉求不同，拆开后可以独立限流和扩缩；decode 端更容易守住在线延迟；系统边界更清晰，SLO 也更可控。
6. vLLM 的瓶颈通常出现在什么阶段？
   回答要点：长请求更容易卡在 prefill 和 KV cache 管理，短请求更敏感于 decode 和调度开销；实际瓶颈常见于 attention、cache 访存和 CPU 侧 launch overhead。

### 3.4 vLLM 你至少要会的关键词

- PagedAttention
- block table
- KV cache manager
- continuous batching
- chunked prefill
- prefix caching
- CUDA/HIP graph
- tensor parallel
- quantization
- speculative decoding
- disaggregated prefill

## 4. SGLang 需要掌握什么

SGLang 在面试里经常和 vLLM 放在一起比较。你要知道它的定位差异。

### 4.1 核心定位

SGLang 更强调：

- 前端表达能力
- 结构化输出
- agent / tool calling 场景
- prefix reuse
- hierarchical KV cache
- router / gateway / multi-instance deployment

### 4.2 必会概念

#### RadixAttention

你要能讲：

- SGLang 侧重 prefix reuse
- Radix tree 思路适合多轮对话 / 共享前缀很强的 workload
- 它和 vLLM 的 PagedAttention 重点不同

#### HiCache

你要能讲：

- GPU memory、host memory、distributed storage 分层缓存
- 类似 CPU cache hierarchy 的设计思路
- 目标是把 KV cache 做成更完整的层级系统

#### Structured outputs

你要能讲：

- JSON schema / regex / EBNF 约束输出
- 对 tool calling / agent 很重要
- 会引入 grammar backend 和 constrained decoding 问题

#### Speculative decoding

你要能讲：

- draft / target 两阶段
- EAGLE / MTP / ngram / classic draft 等不同路径
- 本质上是减少 target model 实际解码步数

#### PD disaggregation

你要能讲：

- prefill 和 decode 物理分离
- router / gateway 的作用
- 为什么 disaggregation 对 TTFT 和 TPOT 都有价值

#### Expert parallelism

你要能讲：

- MoE 模型需要 expert parallel
- 需要 all-to-all / grouped GEMM
- 这是 SGLang 在 MoE serving 里很重要的一块

#### Benchmark / profiling

你要能讲：

- TTFT、TPOT、ITL、throughput
- steady-state 需要 warmup
- 不能拿冷启动当最终结果

### 4.3 SGLang 面试常追问

1. RadixAttention 和 PagedAttention 的差异是什么？
   回答要点：RadixAttention 更强调 prefix reuse 和 radix tree 式共享，适合多轮对话和共享前缀很多的场景；PagedAttention 更强调 block/page 化的 KV 管理和通用 serving 调度。
2. HiCache 为什么适合多轮对话和长上下文？
   回答要点：因为它把 KV cache 做成分层缓存体系，热前缀更容易留在高性能层；多轮对话的重复前缀命中率高，层级缓存能把这种收益放大。
3. structured output 的 grammar backend 怎么理解？
   回答要点：它本质上是把输出约束在语法空间里，例如 JSON、regex 或 EBNF；解码时对非法 token 做 mask；适合 tool calling 和严格格式输出。
4. speculative decoding 的收益来自哪里？
   回答要点：小 draft model 先提案，大模型批量验证；如果接受率高，就能减少大模型逐 token 解码次数；收益来自把“逐步生成”变成“批量校验”。
5. PD disaggregation 为什么对 tail latency 有帮助？
   回答要点：把 prefill 和 decode 拆开后，长 prefill 不会直接拖慢 decode；在线路径更稳定，尾延迟更容易控制。
6. MoE 模型在 serving 上为什么需要 expert parallel？
   回答要点：MoE 的专家通常分布在多个设备上，token 路由后需要跨设备计算和通信；expert parallel 是把专家计算拆开并行化的基础，不然单卡很难承载。

### 4.4 SGLang 你至少要会的关键词

- RadixAttention
- HiCache
- structured outputs
- tool parser
- reasoning parser
- speculative decoding
- PD disaggregation
- model gateway
- expert parallelism
- benchmark / profiling

## 5. Mooncake / KV cache disaggregation 需要掌握什么

Mooncake 是另一个特别适合 AI infra 面试讲的方向，因为它非常聚焦于：

- KV cache
- prefill/decode disaggregation
- 资源池化
- SLO 和吞吐的权衡

### 5.1 核心定位

Mooncake 的关键词是：

- KVCache-centric
- disaggregated architecture
- prefill cluster / decode cluster separation
- distributed KV cache pool

### 5.2 必会概念

#### 为什么是 KVCache-centric

因为 serving 里真正重的是：

- 历史上下文
- KV 复用
- cache 迁移
- 长上下文 reuse

Mooncake 的设计不是围绕“跑一次 forward”展开，而是围绕“如何高效管理 KV 资产”展开。

#### Prefill / Decode 分离

你要能讲：

- prefill 更偏计算
- decode 更偏交互延迟
- 分离可以按阶段调资源

#### KV transfer / pool / storage tiers

你要能讲：

- 不是所有 KV 都留在 GPU
- CPU DRAM、SSD 甚至分布式存储都可以作为层级池
- 关键在于迁移、命中、回收和调度

#### SLO / early rejection

你要能讲：

- 超载场景不能假设每个请求都必须接
- 需要基于预测做拒绝或延后
- 这是 serving 系统里非常真实的工程问题

### 5.3 Mooncake 面试常追问

1. 为什么 Mooncake 要把 KV cache 当成第一类资源？
   回答要点：因为 serving 里的核心资产不是单次 forward，而是上下文状态；KV cache 决定复用、迁移、容量和 SLO；Mooncake 的设计就是围绕这个资源做池化和调度。
2. prefill 和 decode cluster 为什么要分开？
   回答要点：prefill 更偏计算吞吐，decode 更偏交互延迟；拆开后可以分别扩缩、限流和优化；资源域分离后更容易守住在线体验。
3. KV cache pool 为什么不是简单做一个 Redis 式缓存？
   回答要点：因为 KV cache 有明确的 tensor layout、device affinity 和时延要求；它不是普通 key-value；还要处理 block 粒度、生命周期、迁移和回收。
4. 资源过载时为什么需要 early rejection？
   回答要点：如果什么请求都接，排队会拖垮整体 SLO；提前拒绝或延后能保护核心流量；这是 serving 系统里常见的过载控制策略。
5. 长上下文 workload 为什么更能体现 Mooncake 的收益？
   回答要点：长上下文会放大 KV cache 占用、传输和复用问题；分离式架构越能体现 cache pool 和 handoff 的价值；短上下文下收益不一定明显。

### 5.4 Mooncake 你至少要会的关键词

- KVCache-centric
- disaggregated prefill
- prefill cluster / decode cluster
- distributed KV cache pool
- resource pooling
- early rejection
- SLO-aware scheduling

## 8. 面试高频题库

### 基础题

1. 为什么推理要分 prefill 和 decode？
   回答要点：prefill 负责把 prompt 编进 KV cache，计算量大但并行度高；decode 负责逐 token 生成，计算量小但更依赖 KV 读取和调度；两者瓶颈不同，所以优化方法也不同。
2. KV cache 解决什么问题？
   回答要点：它避免 decode 每一步都重算历史 token 的 K/V；本质上是用显存换算力和时延；是推理加速最核心的状态缓存。
3. 为什么 decode 常常 memory-bound？
   回答要点：因为每步只生成一个 token，算力利用率不高，但要反复访问历史 KV cache；瓶颈更容易落在显存带宽、访存模式和 cache 组织上。
4. PagedAttention 解决什么问题？
   回答要点：它把 KV cache page/block 化，减少碎片和连续大块管理成本；也更适合多请求并发和动态调度；是 serving runtime 的基础能力之一。
5. chunked prefill 为什么能降低尾延迟？
   回答要点：长 prompt 切块后不会一次性占住 GPU；decode 和短请求可以插入执行；因此尾部延迟更稳，TTFT 也更好控制。
6. 为什么 CUDA Graph 更适合 decode？
   回答要点：decode 的输入 shape 和控制流更稳定，适合 capture 成固定图；这样能减少 launch overhead 和 CPU 调度；prefill 的 shape 变化太大，不如 decode 适合。
7. prefix caching 适合什么场景？
   回答要点：适合系统 prompt、多轮对话、agent prompt 和共享前缀很重的 workload；它的收益主要体现在 TTFT 和重复请求成本上。
8. 为什么 continuous batching 比静态 batching 好？
   回答要点：静态 batching 要等一批结束再换下一批，GPU 容易空转；continuous batching 允许新请求动态进入，吞吐和利用率更高。

### 进阶题

9. vLLM 的 PagedAttention 和 SGLang 的 RadixAttention 有什么区别？
   回答要点：vLLM 更强调 block/page 化 KV 管理和通用 serving 调度；SGLang 更强调 prefix reuse 和 radix tree 式共享；两者都在解决 KV 复用，但重心不同。
10. HiCache 为什么要做三层缓存？
   回答要点：因为 KV cache 热点程度不同，单层缓存不够灵活；分层后可以把最热状态放在 GPU，把次热状态放在 CPU 或更低成本介质；目标是更高命中率和更低成本。
11. PD disaggregation 的 handoff 边界应该包含什么？
   回答要点：至少要有请求元数据、context length、block table、KV 状态引用或快照、采样相关状态；边界设计的核心是保证 decode 端能无歧义恢复上下文。
12. Mooncake 为什么强调 KVCache-centric？
   回答要点：因为 serving 的关键不是单次 forward，而是历史状态资产；把 KV 作为核心资源，才能把调度、迁移、复用和容量规划串起来。
13. MoE 推理时为什么会遇到负载不均和通信瓶颈？
   回答要点：token 路由不均会导致部分 expert 热点过高；专家分散在不同设备时又会产生 all-to-all 通信；所以 MoE serving 往往是算力和通信双瓶颈。
14. DeepSeek-V2 / V3 为什么对推理优化很有代表性？
   回答要点：它们把 MoE、高效 attention、长上下文和工程优化结合得很紧；特别适合作为“模型结构如何影响 infra 设计”的例子。
15. Structured outputs 为什么会影响解码路径？
   回答要点：因为输出不再是自由采样，而是受 grammar 约束；解码时要做 token mask 或状态机检查；这会增加额外控制逻辑和性能开销。
16. speculative decoding 为什么能提速？
   回答要点：因为小模型先生成候选，大模型一次验证多个 token；如果接受率高，就能显著减少大模型实际 decode 次数；瓶颈从“逐 token 生成”变成“批量验证”。

### 工程题

17. 如何估算 KV cache 显存？
   回答要点：按 `2 * layers * batch * seq_len * kv_heads * head_dim * bytes` 粗算，再乘 block 对齐和碎片损耗；其中 `2` 是 K/V 两份；`kv_heads` 要注意 GQA/MQA。
18. 如何设计 benchmark 才能证明 steady-state 收益？
   回答要点：要把 warmup 和正式计时分开；固定 prompt、batch 和 bucket；输出 TTFT、ITL、throughput、p50/p99；否则很难区分冷启动和 steady-state 收益。
19. 如何定位 prefill / decode 的主要瓶颈？
   回答要点：先看 profile，再看 attention、cache 读写、launch overhead 和 Python 开销；prefill 更看并行计算，decode 更看 memory 和调度；必要时再上 kernel 级 profiler。
20. 如何验证优化没有破坏正确性？
   回答要点：要做对拍，至少和 monolithic 实现、HF 或官方参考实现比输出 token；混合长度、边界 token、不同 batch 都要测；不能只看单一 prompt。
21. 如果 GPU OOM，你先看什么？
   回答要点：先看 batch、上下文长度、KV cache 预留和模型权重占用；再看是否有重复模型实例或错误缓存保留；如果是 serving，还要看峰值并发和碎片。
22. 如果 decode 延迟升高，你怎么排查？
   回答要点：先看 graph 是否失效、batch 是否变大、cache 命中是否下降、host 同步是否增多；再看 attention kernel、KV 读取和调度开销；最后查是否有不必要的数据搬运。
23. 如果长短 prompt 混合时结果漂移，你怎么分析？
   回答要点：先区分是数值误差、调度差异还是状态污染；对比单独运行和混合运行的中间层输出；重点看 context_len、slot_mapping、block_table 和 cache 边界是否一致。
24. 如果 PD handoff 后输出对不上，你怎么定位？
   回答要点：先检查 payload 元数据是否齐全，再检查 KV 快照是否完整，最后看 decode 端恢复时的 block_table、context_len 和采样状态；很多问题都出在边界语义不一致。

### 系统设计题

25. 如何设计一个支持 chunked prefill 的 serving runtime？
   回答要点：先把请求切成 prompt chunk 和 decode step 两种调度单元；再设计 token budget、优先级和抢占规则；最后保证 chunk 之间的状态能正确衔接。
26. 如何设计一个支持 prefix cache 的调度器？
   回答要点：要有 prefix hash、block 复用、命中统计和回收机制；还要处理不同请求的前缀共享和失效问题；最终目标是缩短 TTFT。
27. 如何设计一个稳定的 CUDA Graph steady-state 路径？
   回答要点：先限定固定 bucket，再做 warmup capture；graph replay 期间尽量避免 host 同步和动态 shape；同时保留 fallback 路径处理非稳定请求。
28. 如何设计一个同机 shared memory KV handoff？
   回答要点：prefill 侧把 KV 快照放进共享内存，decode 侧通过引用恢复；metadata 和数据面分离；重点是协议、生命周期和跨进程一致性。
29. 如何设计一个跨节点 disaggregated prefill 系统？
   回答要点：需要定义 KV 传输协议、cache pool、调度器和恢复逻辑；还要考虑带宽、压缩、容错和 SLO；本质上是把 KV 资产做成分布式资源。
30. 如何为 MoE 模型设计 serving runtime？
   回答要点：要支持 expert routing、负载均衡、通信优化和 expert parallel；还要考虑热点 expert 和动态 batch；MoE 的服务端难点是算力和通信同时存在。

## 9. 面试经验总结：常见考察模式

结合公开面经和 AI infra 岗位常见问法，常见模式是：

### 9.1 先概念，再追细节

比如：

- 什么是 KV cache？
- 为什么要 PagedAttention？
- block table 是什么？
- 为什么 chunked prefill 有收益？

### 9.2 先框架，再实现

比如：

- vLLM 的优势在哪里？
- SGLang 为什么适合 agent / structured output？
- Mooncake 的分离式架构解决什么问题？

### 9.3 先正确性，再性能

比如：

- 你的优化会不会影响输出？
- 怎么做对拍？
- steady-state 和 cold start 怎么分开？

### 9.4 先局部，再系统

比如：

- 你怎么优化 attention？
- 你怎么优化调度？
- 你怎么把 prefill / decode 拆掉？
